CareerOS

A local desktop app for job search that builds tailored CVs from verified facts only, so it cannot invent claims.

The problem

Tailoring a CV for every role by hand is slow, and AI tools are happy to invent metrics. A CV that cannot survive a background check is worse than none.

My role

Product owner, designer and builder. I wrote the build brief and the rules the system must never break, and I am building it milestone by milestone.

Product decisions

  • The database itself enforces that only verified facts can appear on a CV.
  • The AI only selects and orders pre verified bullets. It never writes new claims.
  • Local first, because a job search holds private data.
  • Milestones with gates. Each milestone ends with automated checks before the next one starts.

Challenges and what I learned

  • Making the rule structural. A prompt that says do not invent can be ignored, so the constraint sits in the data layer.
  • Reproducing a CV template exactly. The golden render test catches layout drift.
  • Keeping real personal data out of the repository. Inputs are git ignored and tests use synthetic fixtures.

Results

  • Fact base and verified fact rules are built and tested, and the template render passes its golden check. The full paste a job description to approved CV flow is next.

1. Overview

A local desktop app for job search. I paste a job description, approve it once, and receive a truthful, correctly formatted CV in my master template, tracked in a local pipeline. The AI may only select and order facts that I have already verified, and the database refuses to let anything else reach a CV.

2. Goals and non goals

Goals

  • Tailor a CV to a role in minutes without fabricating a single claim.
  • Produce Word and PDF files that need zero manual layout fixes.
  • Keep every job search record on my own machine.
  • Track each application through eight clear states.

Non goals

  • No scraping of job boards. Their terms prohibit it, so discovery uses public employer feeds and manual import.
  • No automatic submission. Nothing is ever applied for without me.
  • No cover letters, email parsing, analytics or sync in the MVP.
  • No multi user support and no Windows build in the MVP.

3. Users and needs

Me, the job seeker

Tailor applications quickly while staying able to defend every line in an interview or background check.

Anyone with the same problem

A reference design for AI assisted applications that cannot invent claims.

4. User stories

  • As a job seeker, I want to import my master CV as individual facts, so that I can verify each one once and reuse it.
  • As a job seeker, I want to paste a job description and see which verified facts answer each requirement, so that I know where I am strong and where I have gaps.
  • As a job seeker, I want one approval click before generation, so that I stay in control without extra steps.
  • As a job seeker, I want export blocked if any bullet cannot be traced to a verified fact, so that I never send an unsupported claim.

5. Functional requirements

P0 is required for the first release. P1 follows. P2 needs evidence first.

F1P0

Fact base

Every CV usable fact has a source, a date range and a verification status.

Acceptance: Unverified facts cannot reach a CV. The rule is enforced twice, by a database constraint and by the single query path for eligible facts.

F2P0

Template capture

The master Word document becomes a template with placeholders, A4 with justified body text.

Acceptance: A render with the original content is visually identical to the master. The golden test matched 46 of 46 paragraphs in text and formatting.

F3P0

Job intake

Paste a job description, or fetch a public page and confirm the text.

Acceptance: A stored job record with title, company, location, raw text and first seen date.

F4P0

Requirement extraction

The description becomes structured data separating mandatory from preferred requirements, years, certifications and location or visa rules.

Acceptance: Output is validated against a schema. Invalid output is retried once, then flagged.

F5P0

Fit assessment

Hard filters, then a weighted score from 0 to 100 with reasons for and against, citing fact IDs.

Acceptance: A failed mandatory requirement shows Disqualified regardless of score. The label says suitability score, never chance.

F6P0

CV generation

The model returns content that references fact IDs only. A renderer fills the template.

Acceptance: Word and PDF files are saved to the application folder.

F7P0

Quality gate

Automatic checks before export.

Acceptance: Export is blocked if any bullet lacks a fact ID, any date differs from the fact base, the page count exceeds the variant limit, or the PDF text is not extractable.

F8P0

Tracker

Eight states: Saved, Approved, Docs ready, Applied, Screening, Interview, Offer and Closed with a reason.

Acceptance: A timestamp on every state change, plus notes and a follow up date.

F9P1

Cover letters, batch approval and employer feeds

Cover letters under the same fact rule, a queue of up to ten jobs, and public feeds for a list of target employers.

Acceptance: Starts only after the MVP exit test passes.

F10P2

Email and calendar matching, interview prep and outcome intelligence

Read only matching with review for low confidence results, and outcome analysis.

Acceptance: Needs real outcome data, at least 30 tracked applications, before it is meaningful.

6. Non functional requirements

Shell
Tauri 2 with React and TypeScript for a small local app with keychain access.
Storage
SQLite with migrations in the repository. Local first with no operations to run.
AI boundary
One AI provider. The model returns structured JSON only, and every bullet references a fact ID. This rule is never revisited.
Secrets
The API key lives in the macOS keychain. Model calls run from the native side so the key never enters the interface.
Rendering
The master Word file is filled by a template engine to preserve fonts and spacing, and PDFs are produced by a headless converter.
Privacy
Real personal inputs are git ignored. Tests use synthetic data only.
Testing
Unit tests for migrations, database constraints and fact eligibility, Rust tests, a smoke run, and a golden file comparison for the template.
Cost
Every model run logs its cost.

7. Scope

In scope

  • Single user on one Mac
  • Fact import from one master CV and manual review
  • Job intake, requirement extraction, fit assessment and CV generation
  • Two CV variants, product manager and PMO or delivery
  • Local tracker with eight states

Out of scope

  • Scraping of job boards
  • Cover letters, analytics and LifeOS integration
  • Cloud backend, sync and Windows
  • Template designer and multiple layouts

10. Risks and mitigations

Fact verification stalls the project.

Mitigation: M2 can run on the subset of facts already verified.

Template drift between app output and the master.

Mitigation: A golden render comparison on every change.

Invalid model output.

Mitigation: Schema validation, one retry, then flag the result.

Unevidenced metrics in my history.

Mitigation: Unevidenced numbers stay unquantified until I can source them.

Model cost grows.

Mitigation: A cost log per run and a monthly ceiling.
